# 《占城大师》地图与地块生成机制

研究基准：配置/界面快照 2026-09-03；函数级逆向基准 2026-09-11；资源版本 `1.4.15.558-preview`。本文只对当前已恢复的客户端主链负责；未抓取当前线上对局载荷，因此服务器实验、账号分流和模式级覆盖仍需单独验证。

## 一页结论

理解这套系统最重要的一点，是把“地图生成”“地块显现”“玩家点击”分成三个阶段。当前代码证据更支持下面这条主线：

```text
地图/模式确定地图骨架
→ 初始化所有参与生成的格子
→ 普通格先确定 25 / 50 / 100 / 250 价格档位
→ 再按该档位权重确定 R / SR / SSR / SSSR / 空
→ 再从合法候选中选择具体建筑
→ 把基础隐藏结果保存到格子状态
→ 玩家扩张后，附近格子进入可见/可开启状态
→ 玩家真正点击时读取已有隐藏结果
→ 少量点击阶段规则仍可能降级、升级或覆盖最终展示结果
```

因此，这页不再把“随机”当成一个动作。实际至少有三层随机：**先随机地块档位，再随机稀有度，再随机具体隐藏建筑**。最关键的是：**第三层也通常发生在初始化。第三层结束后，这个格子的基础“底牌”已经具体到某一个 Architecture，而不是只保存一个 SR / SSR 标签等玩家点击时再抽。** 玩家后来看到或点击这个格子，通常不是这三层随机第一次发生的时点。

|层次|回答的问题|主要发生阶段|
|---|---|---|
|地图骨架|这局是哪张图、主城和固定格在哪里|对局建立时|
|地块档位|这个普通格是25、50、100还是250|初始化|
|基础隐藏稀有度|这个档位里抽到R/SR/SSR/SSSR还是空|初始化|
|基础隐藏建筑|在该稀有度的合法候选中具体选中哪一个 Architecture|初始化；选完后写入格子状态|
|显现/可开启|这个格子什么时候出现在扩张边界、什么时候能点|对局进行中|
|最终揭晓结果|玩家点开后最后实际得到什么|点击时；通常沿用基础隐藏建筑，但存在少量后置覆盖|

例如一个普通格在初始化时抽到100金币档，再抽到SR，当前有3个合法SR建筑A / B / C，第三层随后随机选中B并把它保存到格子状态。玩家以后扩张到这里时可能只先看到“100金币”，但真正点击时通常是**揭晓已经保存的B**，不是这时才重新从A / B / C里抽一次。

这里还有一个明确的运行时例外：**符合条件的未打开隐藏格在所有权变化时会进入“第二次生成”**。这次不会重抽25/50/100/250价格档，而是保留原价格，按新归属方可用候选重新抽内部稀有度和具体隐藏内容；详见5.4。

还要把**外部组卡规则**和**战斗内部生成规则**分开理解。正常玩家在卡组编辑界面不能把牌组配成全SSSR：实测与本地化键`CantEquipCardTip`共同表明，卡组至少要保留1张R（绿色）、1张SR（蓝色）、1张SSR（紫色）。但战斗内部的地块稀有度权重并不会因为这个UI限制而改写；它仍按`GlobalHexInfo`先抽内部稀有度，再去当前战斗牌组中寻找合法候选。正常产品规则与异常/调试边界的区别详见第3节。

如果只想先理解一块普通地从生成到底牌揭晓的主流程，读第1～5节即可；第6节以后主要是加权、seed、地图池和证据细节。

## 1. 一个普通地块从出生到被玩家打开

### 1.1 初始化：先生成基础隐藏结果

`BuildInitialSetupNormalized`会规范化地图模板、双方牌组和主城，再由`BuildStableGenerationOrder`确定内部逐格处理顺序。普通格进入`BuildCellContent`后，主要按下面的顺序生成：

```text
确定地块档位
→ 根据档位读取稀有度权重
→ 应用当局有效的稀有度修正
→ 抽出 R / SR / SSR / SSSR / 空
→ 从本局合法候选中选择具体建筑
→ 解析价格和内容
→ 保存到 BattleHexCellState
```

这里的“保存”很关键。当前主链不是等玩家以后点到这个格子时，才从零开始决定它是什么；多数普通格在初始化阶段已经完成“价格档位 → 内部稀有度 → 具体隐藏建筑”三步，并把结果保存到格子状态。也就是说，第三层结束时底牌通常已经具体到某一个建筑。

### 1.2 扩张显现：出现不等于重新随机

玩家打开边界格后，附近格子可能因为出现新的本方 opened anchor 而满足开放条件。`GetHexOpenBlockReason`除了读取目标格自己的`CanOpen`，还会调用`HasPlayerOpenAnchorNeighbor`检查`Neighbors`中的已开格、主城和阵营状态。

所以典型过程更接近：

```text
开局时：B / C / D 已经有档位和隐藏内容
A 尚未打开：B / C / D 还不满足当前扩张条件
玩家打开 A
→ A 成为新的 opened anchor
→ B / C / D 满足邻接开放条件
→ UI开始显示这些格子的价格或可操作状态
```

这一步是“让已有格子进入视野/开放边界”，不是重新给B/C/D各掷一次25%。关于Q/R坐标和六邻格，可单独看[Q/R六边形坐标概念专题](../hex-coordinates/index.html)。

### 1.3 玩家点击：通常读取隐藏结果，再做少量后置处理

玩家点击目标格的已确认主链为：

```text
OpenHex
→ GetHexOpenBlockReason
→ SpendGold
→ CommitOpenedHex
→ ResolveOpenedHexOutcome
```

`ResolveOpenedHexOutcome`接收的是已经存在的`BattleHexCellState`。正常兵营路径优先通过`SelectCardForCellArchitecture`按格子保存的隐藏建筑去匹配卡牌；内容缺失或无法匹配时才走`SelectCardForHex`回退。当前开格主链里没有再次执行决定普通四档的`Range(0,4)`；函数RVA / wasm定位统一放到后面的证据索引，不作为理解玩法的前置条件。

因此最准确的说法不是“开局已经完全锁死一切”，而是：**开局已经生成基础隐藏结果；玩家点击时通常只是结算和揭晓，但少量明确规则仍可以改写最终结果。** 如果一个仍未打开的隐藏格在点击前发生符合条件的所有权变化，它还可能先经过5.4所述的占领重生成，再由后续点击揭晓新的隐藏结果。

## 2. 一个普通格在初始化时到底决定了什么

对普通格来说，最容易理解的方法不是记函数名，而是把“基础底牌”和“最终揭晓”分开。**初始化阶段通常已经把基础底牌生成到具体建筑；点击阶段通常只是揭晓和结算这张底牌。**

可以先记住四个概念：

|概念|例子|通常什么时候决定|
|---|---|---|
|价格档位|100金币|初始化|
|基础隐藏稀有度|SR|初始化|
|基础隐藏建筑|SR建筑B / 某个具体`ArchitectureId`|初始化，第三层完成后保存|
|最终揭晓结果|玩家实际点开后得到的建筑/卡|点击时；通常等于基础隐藏建筑，但可能被少量规则覆盖|

因此，“第三层随机具体合法候选”不是在说“先记住SR，等玩家点的时候再从SR里抽一张”。它是在说：**初始化已经抽到SR以后，马上继续在合法SR候选里选出某一个具体建筑，并把它作为这个格子的基础隐藏内容保存。**

### 2.1 第一层：先决定25 / 50 / 100 / 250价格档

没有被固定用途、模板内容或特殊资源提前占用的普通格，会在`ResolveInitialRarity`进入：

```text
quality = Range(0,4)
```

四个整数等概率，因此“真正走到普通档位随机”的格子，第一层各25%：

|Quality|玩家后来看到的档位|基础价格|第一层概率|
|---:|---|---:|---:|
|0|一星|50|25%|
|1|二星|100|25%|
|2|三星|250|25%|
|3|问号|25|25%|

这里的25%只针对普通随机格，不代表整张地图最终四种价格各占25%。主城邻格、模板固定格、特殊资源、防御和金矿等都会提前改变整图构成。

### 2.2 第二层：根据价格档抽基础隐藏稀有度

第一层确定档位后，系统读取`GlobalHexInfo`中的基础权重：

|地块档位|基础价格|R|SR|SSR|SSSR|空|
|---|---:|---:|---:|---:|---:|---:|
|一星1001|50|74|20|5|1|0|
|二星1002|100|50|40|8|2|0|
|三星1003|250|0|0|90|10|0|
|问号1004|25|0|0|15|5|80|

这里抽出来的是**这个格子的基础隐藏稀有度**，还不是具体建筑。例如100金币格可能在第二层抽到SR；问号格则可能直接抽到“空”。R / SR / SSR / SSSR表示卡牌/建筑的稀有度层级，不是卡牌自身的养成等级。

这一步与第一层是连续的两次决策。例如忽略其他修正时，“一个任意普通格最终先成为问号，并在问号档抽到SSSR”的基础概率是：

```text
25%（第一层成为问号） × 5%（第二层问号里抽SSSR） = 1.25%
```

### 2.3 第三层：初始化时选定并保存具体隐藏建筑

如果第二层得到的是R / SR / SSR / SSSR，而不是空，系统会继续进入`ResolveRandomArchitecture`。这一步仍然属于**初始化**，目的就是把“一个稀有度标签”变成“这个格子的具体基础底牌”。

候选会继续经过以下过滤：

1. 稀有度必须匹配第二层结果；
2. 当前`hexType` / 固定用途必须允许；
3. 问号格排除金矿和防御建筑；
4. 金矿额度耗尽后排除随机金矿；
5. 其他当前模式和候选合法性条件必须满足；
6. 候选规范化并排序后，使用`Range(0,candidates.Count)`选择其中一项。

当前没有发现这一层给单张普通候选配置额外独立权重。如果有N个完全等价的合法候选，条件概率就是1/N。

最重要的是：**选中以后，具体建筑会被写进格子状态，成为这个格子的基础隐藏内容。第三层结束时，“底牌”通常已经具体到某一个`Architecture`。**

例如：

```text
地图初始化处理某格
→ 第一层：抽到100金币
→ 第二层：100档抽到SR
→ 第三层：当前合法SR建筑有A / B / C
→ 随机选中B
→ 把“100金币 + SR + 建筑B”保存到BattleHexCellState

之后玩家扩张到这里
→ UI可能只先显示“100金币”

玩家真正点击
→ 通常读取并揭晓已经保存的建筑B
→ 不是此时重新从A / B / C里再抽一次
```

牌组缺失或为空时仍存在从战斗配置包回退的分支，所以不能把所有模式都简化成“第三层永远只从玩家装备牌组里抽”；但对于正常带入牌组的PVP理解，当前战斗Loadout是最重要的候选来源之一。

### 2.4 三层结束以后，基础底牌已经生成；点击通常只是揭晓

把前三层连起来，一个普通格的主流程就是：

```text
初始化
  第一层：决定价格档位
      ↓
  第二层：决定基础隐藏稀有度
      ↓
  第三层：决定具体基础隐藏建筑
      ↓
  写入格子状态，基础底牌生成完成
      ↓
对局扩张
  格子进入可见 / 可开启范围
      ↓
玩家点击
  读取基础底牌并结算 / 揭晓
      ↓
  少量点击阶段规则可能覆盖最终结果
```

所以后文出现“低价重抽”“超级召唤”“神器”“fallback”时，应把它们理解为**点击阶段对既有底牌的替换、修正或兜底**；出现“占领隐藏格重生成”时，则是**在玩家点击之前，把旧底牌重新生成一遍并重新保存**。它们都不是普通情况下“玩家点击时才第一次决定这个格子是什么”。

## 3. 卡组如何影响第三层候选

卡组会影响“第三层有哪些合法具体建筑可选”，但**不会反过来改写第一层价格概率或第二层基础稀有度权重**。这一点要把“玩家在界面上允许带什么”与“战斗系统拿到Loadout以后怎样生成底牌”分开。

### 3.1 外部组卡规则：正常玩家至少保留R / SR / SSR各1张

客户端本地化表存在：

```text
CantEquipCardTip = 卡组必须包含至少1张{0}卡牌
```

结合实际卡组编辑表现，正常玩家至少必须保留：

|玩家看到的颜色|内部稀有度|正常卡组最低数量|
|---|---|---:|
|绿色|R|至少1张|
|蓝色|SR|至少1张|
|紫色|SSR|至少1张|
|金色|SSSR|当前没有发现同类“至少1张”的要求|

对应界面类为`CardDeckChangePanel`，恢复到的关键方法包括`ChangeEquipCard`、`UpdateCardDeck`和`UpdateShowCardTypeCountUI`。因此，对正常玩家路径来说，“全SSSR非空卡组”不是一个合法的UI配置。

### 3.2 这条UI限制是在保证输入条件，不是在改变50 / 100格概率

即使UI要求至少一张R、一张SR、一张SSR，战斗内部仍然是：

```text
价格档位
→ 按该档位原权重抽R / SR / SSR / SSSR / 空
→ 用抽中的稀有度 + hexType等条件筛当前Loadout候选
→ 第三层选具体建筑并保存
```

所以50金币仍按74 / 20 / 5 / 1抽R / SR / SSR / SSSR，100金币仍按50 / 40 / 8 / 2抽。**外部组卡规则更像是在为第三层提供一个更完整的候选输入前提，而不是修改第二层概率表。**

### 3.3 “各至少1张”不等于任何格子都一定有候选

正常卡组里有R / SR / SSR，并不代表每一个`hexType`在每一个稀有度下都一定能找到合法建筑。第三层还要经过类型、固定用途、问号排除、金矿额度等过滤。

因此仍可能出现：第二层抽到某个稀有度，但当前具体格子在这个稀有度下没有合法候选。`SelectCardForCellArchitecture`失败后再进入`SelectCardForHex`等fallback，仍然是有意义的运行时兜底，并不会因为UI做了最低配卡限制就彻底不可达。

### 3.4 “全SSSR卡组”只保留为异常输入边界，不再作为正常策略

如果通过调试、旧数据、异常载荷、回放或其他绕过正常组卡界面的方式，真的把一个“非空且全部是SSSR”的Loadout交给战斗层，第二层也**不会自动变成100% SSSR**。

例如50金币格仍可能先抽到R：

```text
50金币
→ 第二层抽到R
→ 第三层尝试找合法R建筑
→ 全SSSR异常Loadout里没有R候选
→ 基础隐藏建筑可能缺失 / 无法正常匹配
→ 玩家点击时进入fallback
→ 若当前合法替代候选只有SSSR
→ 最终可能揭晓SSSR
```

所以“最终可能得到SSSR”和“地图初始化时已经把这个格子生成成SSSR”是两回事。前者可能是点击fallback的结果；后者只有第二层本来就抽到SSSR并且第三层成功选中具体SSSR建筑时才成立。

前三次低价格保护同样不能凭空生成玩家没有的R卡；异常Loadout没有R候选时，降级替换可能失败。但这只能视为底层异常输入的代码边界，不能写成正常玩家可利用的组卡策略。

### 3.5 战斗入口还有Loadout校验，但当前不能证明它重复强制“绿蓝紫各1张”

BattleCore存在`PlayerBattleLoadoutValidator.ValidateCards(...)`，说明战斗入口还会做独立的Loadout合法性检查。当前恢复的函数体更像是在验证卡牌ID、配置引用等载入合法性；目前没有足够证据确认它还会再次执行与组卡UI完全相同的“R / SR / SSR至少各1张”规则。

因此后续研究正常实战出卡率，应优先使用**UI允许的合法卡组**作为样本空间；只有专门研究容错或异常载荷时，才讨论全SSSR等越过外部组卡规则的输入。

## 4. 不是所有格子都走这套普通三层随机

### 4.1 模板固定内容优先保留

主城、已打开格、不可开启格、已有`ArchitectureId`/`CardId`以及其他显式内容会优先保留。训练和教程也可以直接预置内容，因此这类格子会绕过普通随机的部分或全部步骤。

### 4.2 主城邻格是结构性配额，不是六个普通随机格

系统分别取得双方主城最多6个邻格，并各自执行一次`ShuffleSix`。洗牌决定用途落在哪里，而不是决定有没有这些用途。

|槽位|用途|结果|
|---:|---|---|
|0|GoldMine|强制金矿，按金矿价格|
|1|OneStar|强制一星，50|
|2|UnCharted|强制问号，25|
|3|Defense|强制防御候选，通常250|
|4|Soldier|只有`SoldierPileHiddenHexEnabled`开启时成立|
|5|None|继续走普通随机|

地图边缘、固定内容或缺失邻位会使这套配额不能完整落地；双方独立洗牌也不保证镜像位置相同。

### 4.3 特殊资源会提前占用位置

竞技场至少为4时，初始化存在一次`Range(0,101)`并以结果小于30作为特殊资源事件入口，离散口径为30/101≈29.70%。命中后会从合法候选中选1或2个位置；每选一个位置，就从候选池移除它以及所有相邻格，因此两个特殊资源点不会紧挨着。成功构建特殊格后，该格不再进入普通档位和兵种随机。

`TryBuildSpecialResourceCell`在不同竞技场进入不同内容分支，但具体资源类型字符串所在共享跳板尚未完全恢复，因此这里只确认触发、数量和不相邻保护。

### 4.4 金矿来自多个来源，不能用一个“固定矿数”概括

一张图的初始金矿至少可能来自：模板预置、主城邻格强制金矿、普通R候选中的随机金矿。`CreateGoldMineLimitState`还能读取总额度和镜像侧额度，对“普通候选里的随机金矿”进行限制。

主城邻格的强制金矿可以绕过普通候选封锁，所以该额度不能直接理解成整张地图最终矿数硬上限。旧`GlobalArenaInfoSheet2.minesCountLimit`到当前`BattleConfigPackage`的完整注入关系尚未恢复，也不应把静态表值直接写成线上实测上限。

## 5. 点击时哪些结果仍可能变化

### 5.1 正常路径：沿用初始化隐藏结果

普通情况下，玩家点开格子后不会重新抽25/50/100/250，也不会从零重跑完整的“稀有度→具体卡牌”链。开格函数优先消费已经生成并保存的格子内容。

### 5.2 低价格子存在高品质重抽/降级路径

`TryApplyFirstThreeCheapOpenReroll`这条路径要求目标价格小于250、存在有效候选、已开低价格计数满足`CountCheapOpenedHexesByPlayer<=3`、候选稀有度至少为RareLevel 3，并排除部分资源和防御结果。命中后会尝试从R候选中重新选择，并排除金矿。

因此一个格子初始化时即使已经是SSR/SSSR，最终玩家点开时也可能被这一点击阶段规则改写。25、50、100属于低价范围，250不属于。函数名带“FirstThree”，但完整计数追加时序仍应以当前代码边界为准，因此这里不把它简化成玩家肉眼可直接数出的“严格前三次必降级”。

### 5.3 祝福、神器和引导也可能后置覆盖

- 神器首次传说升级：满足对应开关、候选来自本局牌组、阵营有效且机会未消耗等条件时，可在已有候选基础上尝试替换为传说候选。
- 超级召唤：`SpendGold`成功扣款后累计祝福进度；本地阈值为2000。达到阈值后进入Ready，之后在合法翻格结果处理中消费并尝试选择传说卡。
- 教程/引导：教程可以预置结果；guidedGame的敌方SSSR还存在按当前档位降级的路径，另有龙骑士强制引导。
- 被占领隐藏格：这不是点击阶段才发生的重抽，而是在符合条件的所有权变化时提前重生成隐藏内容；具体见5.4。

### 5.4 被占领隐藏格：价格档保留，内部稀有度与具体内容重抽

这里要先区分玩家视角的“占过以后又能点”和底层authoritative state。`ShouldRegenerateCapturedHiddenHexContent`会排除`IsOpened=true`、不可开启格、双方主城、桥格、资源箱、特殊士兵格，以及部分已有/特殊建筑。也就是说，这条机制**不是把任意已经打开的敌方地块清空后再开一次**；它处理的是所有权发生变化时，仍处于隐藏/未打开状态且允许重生成的captured hidden cell。

当前已经把调用时点追到所有权变化链：

```text
ResolveHexOwnershipFromUnitPresence
→ ApplyHexOwnershipChangeIfNeeded
→ ShouldRegenerateCapturedHiddenHexContent
→ TryRegenerateCapturedHiddenHexContent
→ 保留当前 Price，并由 Price 还原原品质档
→ GetCapturedHiddenHexAvailableRareMask(..., originalQualityRareMask)
→ 去掉新归属方没有合法候选的稀有度档
→ 按剩余权重重新抽内部稀有度
→ TrySelectCapturedHiddenHexCard
→ 写回新的隐藏内容状态
→ 玩家之后真正点击时再走正常 OpenHex 链揭晓 / 结算
```

第一层已经可以明确：**不会重新执行普通格的`Range(0,4)`，25/50/100/250价格档位保留。** 重生成函数直接从当前`Price`恢复原品质，因此同一坐标被捕获后仍然是原来的价格档：

|保留的Price|还原档位|本档基础R|SR|SSR|SSSR|空|
|---:|---|---:|---:|---:|---:|---:|
|25|问号|0|0|15|5|80|
|50|一星|74|20|5|1|0|
|100|二星|50|40|8|2|0|
|250|三星|0|0|90|10|0|

第二层会重抽，但上表不能机械当成每次占领后的最终百分比。`GetCapturedHiddenHexAvailableRareMask`会把原品质允许的稀有度范围和**新归属玩家当前真正存在的合法候选**相交；某个稀有度没有候选时，该权重段不会继续参加这次选择，剩余有效权重按比例重新归一化。例如一个50金币一星格，若新归属方没有任何合法R候选，但SR、SSR、SSSR都存在，那么参与二次随机的权重从`74:20:5:1`变成`20:5:1`，对应条件概率约为76.92%、19.23%、3.85%。

问号格的“空”是本档结果之一，因此25金币格在占领后重生成时仍可能再次抽到空；它不是因为已经经历过一次争夺就必定变成建筑。

第三层也会重选具体内容。`TrySelectCapturedHiddenHexCard`使用新的`playerId`和当前合法候选上下文来构建被占领隐藏格候选，并存在`Exact`、`ExactBarracksRestricted`、`BarracksFallback`等候选/回退模式。因此这里不应理解为“把原来对手已经藏在这个坐标里的那张卡转交给新玩家”；更准确的是：**价格档保留，但内部内容针对新归属方重新建立候选并重新选择。** 同时，由于存在回退分支，也不能把所有模式简化为“永远只从玩家装备牌组中抽”。

这条重生成链没有重新进入开局的`ResolveInitialRarity → ResolveUserLabelGoldCardOdd`用户标签加权链。因此JustPaidUser、LosingStreak、InactiveUser、对手WinningStreak等开局SSSR增量，不会因为一个隐藏格发生所有权变化就在这里重新触发一次；占领重生成使用的是原价格档对应的基础稀有度权重，再叠加“当前哪些稀有度实际有合法候选”的可用性过滤。

最后要把“什么时候随机”和“什么时候揭晓”分开：**二次随机发生在所有权变化时，第二次点击不是才开始随机。** 新隐藏结果写回后，玩家以后真正点击该格，仍进入`OpenHex → GetHexOpenBlockReason → SpendGold → CommitOpenedHex → ResolveOpenedHexOutcome`。因此4.2和4.3列出的低价降级、超级召唤、神器、教程等点击阶段规则，仍可能在这份二次基础隐藏结果之上继续改写最终展示。

所以完整生命周期应写成：

```text
开局生成：价格档 + 初始稀有度 + 初始具体内容
→ 格子保持未打开隐藏状态
→ 所有权变化
→ 若符合 captured hidden 重生成条件：
     保留价格档
     → 按新归属方候选可用性重抽内部稀有度
     → 重选具体隐藏内容
     → 保存新的隐藏结果
→ 玩家之后点击
→ 正常 OpenHex 结算 / 揭晓
→ 少量点击阶段规则仍可覆盖最终结果
```

因此，“开局已经生成整张地图的初始隐藏布局”与“部分未打开隐藏格在占领时进入第二次生成周期”可以同时成立。前者描述初始状态，后者描述运行时所有权变化；二者之间最关键的边界就是：**第二次生成保留第一层价格档，只重做后面的内部内容层。**

## 6. SSSR加权：这是第二层随机的修正，不是另一套地块生成规则

从系统结构看，这部分只是“内部稀有度抽取”的修正层。它不会把25元格改成250元格，也不会决定某格什么时候显现，因此放在普通生成主线之后理解更合适。

### 6.1 用户标签只增加SSSR权重

当前已恢复的用户标签增量为：

|有效标签|加入本方SSSR段的权重|
|---|---:|
|本方JustPaidUser，刚付费|10|
|本方LosingStreak，连败|50|
|本方InactiveUser，回流|30|
|对手WinningStreak，连胜|50|

这些数字是权重增量，不是直接增加百分点。若当前这组增量合计为B：

```text
P(SSSR) = (基础SSSR权重 + B) / (100 + B)
P(其他结果) = 原权重 / (100 + B)
```

例如一星格基础SSSR权重为1；若只存在连败+50，则这一格在加成尚未消费时的SSSR概率为51/150=34%，而不是1%+50%=51%。

### 6.2 这组用户标签是一次性消费资格

`UserLabelGoldCardOddState`按玩家维护共用消费状态。`ResolveUserLabelGoldCardOdd`在消费位已经成立后，不再返回JustPaid/LosingStreak/Inactive/对手WinningStreak这一组加成。当生成结果满足：用户标签加成仍大于0、最终稀有度为SSSR、且HexType属于兵营类时，该玩家消费位会被置为已消费；之后生成格回到不含这组用户标签的权重。

换句话说，它更像“提高本局稳定生成序列里第一个符合条件的SSSR兵营更早出现的机会”，而不是让整张地图每个格永久维持高SSSR率。消费的是本局生成器的加权资格，不等于清除账号上的连败、付费或回流标签。

没有在当前已恢复链路中发现“出一个SSSR后固定冷却N格”“连续N格不出就逐步加概率”“两个普通SSSR必须隔开”等规则。用户标签消费后，基础SSSR概率仍然存在，之后仍可能再生成SSSR。

账号标签如何触发、清除、扣次和进入匹配载荷，由[匹配与机器人专题](../matching/index.html)维护；本页只解释这些状态进入地块生成后如何影响内部稀有度。

每日祝福和周卡加成是在`ResolveInitialRarity`里的独立来源，不属于`UserLabelGoldCardOddState`这一消费位，也不能和上述用户标签机制混成同一个“保底”。

## 7. seed、Q/R和“内部生成顺序”

`BuildStableGenerationOrder`把seed、Q坐标、R坐标和固定常数混合成64位排序键，再按键逐格生成。它不直接等于模板数组顺序，也不等于从主城向外的空间顺序，更不等于玩家点击顺序。

因此：

```text
同一setupId + 同一seed + 同一双方牌组 + 同一战斗配置
≈ 可复现同一初始化结果
```

例如内部生成顺序可能是：

```text
E → B → H → A → F → C → G → D
```

而玩家实际扩张顺序可能是：

```text
A → F → C → D → B → H
```

如果某个一次性SSSR加权在内部第3个生成格H已经命中并被消费，玩家却第6次才扩张到H，那么主观体验会变成“第6次才出金”。反过来若玩家很早摸到H，又会感觉“第一下就出金”。所以玩家第几次看到SSSR，不能直接反推出生成器是第几次才随机到SSSR。

稳定生成顺序也不等于每格完全独立哈希决定全部结果。逐格生成仍会根据候选池、金矿额度、特殊用途等继续消费确定性随机数；前面某格的候选变化可能影响后续随机流。当前初始化链没有读取战斗秒数，时间流逝本身不会逐渐改变已经生成的档位。

Q/R本身只是六边形逻辑坐标，不是概率参数；详细概念见[Q/R六边形坐标概念专题](../hex-coordinates/index.html)。

## 8. 可开启状态属于扩张规则，不属于随机品质

已恢复的`BattleHexCellState`字段包括：

|字段|偏移|含义|
|---|---:|---|
|`IsEnemyHex`|0x22|格子属于哪一侧|
|`IsOpened`|0x23|是否已打开|
|`CanOpen`|0x24|是否具备基础开放许可|
|`IsBridge`|0x25|是否桥格|
|`IsPlayerMainTower`|0x26|是否玩家主城|
|`IsEnemyMainTower`|0x27|是否敌方主城|

`CanOpen`不是“此刻已经出现在玩家边界”的同义词。`GetHexOpenBlockReason`还会调用`HasPlayerOpenAnchorNeighbor(int playerId, BattleHexCellState target)`遍历`Neighbors`，结合邻格的阵营、opened状态和主城状态判断目标格旁边是否存在有效开放锚点。

`CommitOpenedHex`提交后会进入`ResolveOpenedHexOutcome`，并可能触发相邻特殊奖励与`MarkDynamicWallsDirtyAround`刷新动态墙；`BattleNavigationSystem.SetHexOpened`则负责切换opened状态并标记后续刷新。这些属于开格后的状态和拓扑更新，不是普通品质重新随机。

## 9. 地图骨架从哪里来

`BattleSetupConfig`提供一局地图的格子Q/R、邻接、双方主城、可开启状态以及模板预置内容。不同入口选择地图骨架的方式不同：

|入口|当前已确认行为|
|---|---|
|线上对局|`ApplyBattleCoreServerMapSelection`和`TryGetBattleCoreAuthoritativeMapSelection`可接受服务器给出的竞技场、地图类型、多边形ID和setupId，因此客户端不一定自己随机选图|
|离线对局|有preferredSetupId时先精确匹配；否则按入口模式、竞技场、地图类型和多边形ID扫描并返回第一条完整匹配|
|训练局|使用training setupId和固定`hexConfigs`|
|赛季PVP|同层候选`Weight`当前均为1000；首场另有`Pvp_PlayFirstMap=1001`固定矩形图|

普通竞技场在经典三形与多边形之间的上游最终分流仍未完整恢复。因此，配置里存在某张图，不等于当前线上一定由客户端随机选中它。

## 11. 当前证据不能回答什么

- 当前服务器针对具体账号实际下发的seed、地图选择、双方牌组、标签和模式开关。
- 经典三形与多边形在普通竞技场入口的最终上游分流。
- UI从authoritative cell state到具体显隐动画的完整调用顺序；当前初始化与开格主链已支持“基础档位预生成”，但表现层还没有逐函数复原完。
- 旧`minesCountLimit`到当前`BattleConfigPackage`的完整注入关系。
- 分包桥接后的完整OpenHex日志时序，以及超级召唤全部合法目标类型。
- 特殊资源内容字符串和所有候选为空时的端到端边界。
- 被占领隐藏格候选选择中`Exact`、`ExactBarracksRestricted`、`BarracksFallback`等回退模式在所有战斗模式下的完整优先级，以及极端候选全空时最终如何与服务端/UI收口。
- 当前已恢复链路没有发现实时胜率、战斗秒数、固定N格SSSR冷却或固定N格递增保底，但这不能证明所有服务端实验和未恢复分包都绝对不存在这些机制。

## 14. 证据来源与阅读边界

函数级行为结论来自2026-09-11统一主WASM / metadata / C# method-map，并在涉及function-split时交叉检查wasmcode2；静态表和既有界面材料来自2026-09-03本地资源快照。`dump.cs`只用于类型、方法名和RVA定位，不单独作为行为真相。wasmcode2中的`archive_value`仍视为未解释值，不把它当偏移、地址或函数序号。

本页刻意把“玩法解释”和“证据索引”分开：前半部分回答一个格子如何生成和揭晓，后半部分才保留函数、地图池和未确认边界。这样即使以后继续补逆向证据，主叙事也可以继续围绕实际系统决策链，而不是围绕单个历史问题组织。
