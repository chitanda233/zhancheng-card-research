# 《占城大师》地图与地块生成机制

研究基准：配置/界面快照 2026-09-03；函数级逆向基准 2026-09-11；资源版本 `1.4.15.558-preview`。本文只对当前已恢复的客户端主链负责；未抓取当前线上对局载荷，因此服务器实验、账号分流和模式级覆盖仍需单独验证。

## 一页结论

理解这套系统最重要的一点，是把“地图生成”“地块显现”“玩家点击”分成三个阶段。当前代码证据更支持下面这条主线：

```text
地图/模式确定地图骨架
→ 初始化所有参与生成的格子
→ 普通格先确定 25 / 50 / 100 / 250 价格档位
→ 再按该档位权重确定 R / SR / SSR / SSSR / 空
→ 再从合法候选中选择具体建筑
→ 把基础隐藏结果保存到格子状态
→ 玩家扩张后，附近格子进入可见/可开启状态
→ 玩家真正点击时读取已有隐藏结果
→ 少量点击阶段规则仍可能降级、升级或覆盖最终展示结果
```

因此，这页不再把“随机”当成一个动作。实际至少有三层随机：**先随机地块档位，再随机稀有度，再随机具体候选**。而玩家后来看到一个格子、点击一个格子，通常不是这三层随机第一次发生的时点。

|层次|回答的问题|主要发生阶段|
|---|---|---|
|地图骨架|这局是哪张图、主城和固定格在哪里|对局建立时|
|地块档位|这个普通格是25、50、100还是250|初始化|
|内部稀有度|这个档位里抽到R/SR/SSR/SSSR还是空|初始化|
|具体建筑|同稀有度里最终是哪一个合法建筑候选|初始化为主|
|显现/可开启|这个格子什么时候出现在扩张边界、什么时候能点|对局进行中|
|最终展示结果|玩家点开后最后实际得到什么|点击时；通常沿用隐藏结果，但存在少量后置覆盖|

如果只想知道机制本身，读第1～4节即可；第5节以后主要是加权、seed、地图池和证据细节。

## 1. 一个普通地块从出生到被玩家打开

### 1.1 初始化：先生成基础隐藏结果

`BuildInitialSetupNormalized`会规范化地图模板、双方牌组和主城，再由`BuildStableGenerationOrder`确定内部逐格处理顺序。普通格进入`BuildCellContent`后，主要按下面的顺序生成：

```text
确定地块档位
→ 根据档位读取稀有度权重
→ 应用当局有效的稀有度修正
→ 抽出 R / SR / SSR / SSSR / 空
→ 从本局合法候选中选择具体建筑
→ 解析价格和内容
→ 保存到 BattleHexCellState
```

这里的“保存”很关键。当前主链不是等玩家以后点到这个格子时，才从零开始决定它是什么；多数普通格在初始化阶段已经有了基础档位和隐藏内容。

### 1.2 扩张显现：出现不等于重新随机

玩家打开边界格后，附近格子可能因为出现新的本方 opened anchor 而满足开放条件。`GetHexOpenBlockReason`除了读取目标格自己的`CanOpen`，还会调用`HasPlayerOpenAnchorNeighbor`检查`Neighbors`中的已开格、主城和阵营状态。

所以典型过程更接近：

```text
开局时：B / C / D 已经有档位和隐藏内容
A 尚未打开：B / C / D 还不满足当前扩张条件
玩家打开 A
→ A 成为新的 opened anchor
→ B / C / D 满足邻接开放条件
→ UI开始显示这些格子的价格或可操作状态
```

这一步是“让已有格子进入视野/开放边界”，不是重新给B/C/D各掷一次25%。关于Q/R坐标和六邻格，可单独看[Q/R六边形坐标概念专题](../hex-coordinates/index.html)。

### 1.3 玩家点击：通常读取隐藏结果，再做少量后置处理

玩家点击目标格的已确认主链为：

```text
OpenHex（RVA 0x4534 / func[43532]）
→ GetHexOpenBlockReason（RVA 0x4597 / func[6642]）
→ SpendGold（RVA 0x4598 / func[43468]）
→ CommitOpenedHex（RVA 0x459B / func[25588]）
→ ResolveOpenedHexOutcome（RVA 0xF495 / func[25409]）
```

`ResolveOpenedHexOutcome`接收的是已经存在的`BattleHexCellState`。正常兵营路径优先通过`SelectCardForCellArchitecture`按格子保存的隐藏建筑去匹配卡牌；内容缺失或无法匹配时才走`SelectCardForHex`回退。当前开格主链里没有再次执行决定普通四档的`Range(0,4)`。

因此最准确的说法不是“开局已经完全锁死一切”，而是：**开局已经生成基础隐藏结果；玩家点击时通常只是结算和揭晓，但少量明确规则仍可以改写最终结果。**

## 2. 随机到底随机了什么

### 2.1 第一层：普通格的25 / 50 / 100 / 250档位

没有被固定用途、模板内容或特殊资源提前占用的普通格，会在`ResolveInitialRarity`进入：

```text
quality = Range(0,4)
```

四个整数等概率，因此普通格的第一层档位各25%：

|Quality|玩家看到的地块|基础价格|进入普通档位随机后的概率|
|---:|---|---:|---:|
|0|一星|50|25%|
|1|二星|100|25%|
|2|三星|250|25%|
|3|问号|25|25%|

这四个25%只针对“真正走到普通档位随机”的格子，不代表整张地图最终一定有25%的25元格、25%的50元格。主城邻格、模板固定格、特殊资源、防御和金矿等都会提前改变整图构成。

### 2.2 第二层：档位决定内部R / SR / SSR / SSSR / 空权重

`GlobalHexInfo`给出四档基础权重：

|地块档位|基础价格|R|SR|SSR|SSSR|空|
|---|---:|---:|---:|---:|---:|---:|
|一星1001|50|74|20|5|1|0|
|二星1002|100|50|40|8|2|0|
|三星1003|250|0|0|90|10|0|
|问号1004|25|0|0|15|5|80|

每行基础总权重是100，所以在没有额外修正时可以直接按百分比理解。例如：问号格首先有80%基础概率为空，剩余部分才是SSR 15%、SSSR 5%；三星格则不会从这张基础表抽R/SR，而是90% SSR、10% SSSR。

这里的R/SR/SSR/SSSR表示**卡牌/建筑稀有度层级**，不是卡牌自身的养成等级。玩家牌组里某张卡已经升到多少级，是另一套状态，不应和这一层随机混在一起。

这一步和第一层要分开看。比如“任意普通格最终进入问号且内部为SSSR”的基础概率，不考虑其他规则时是：

```text
25%（先成为问号） × 5%（问号里抽SSSR） = 1.25%
```

### 2.3 第三层：同稀有度中再选具体建筑

确定内部稀有度后，`ResolveRandomArchitecture`会从合法候选中继续筛选：

1. 稀有度必须匹配本次抽取结果；
2. 问号格排除金矿和防御建筑；
3. 金矿额度耗尽后排除随机金矿；
4. 固定用途格只保留对应建筑类型；
5. 候选规范化并排序；
6. `Range(0,candidates.Count)`选择其中一项。

当前没有发现这一层给单张候选配置额外独立权重。如果有N个完全等价的合法候选，条件概率就是1/N。牌组缺失或为空时仍存在从战斗配置包回退的分支，因此不能把所有模式都写成“永远只从玩家装备牌组里抽”。

例如问号格已经抽到SSR，且当前有3个完全等价的合法SSR兵营，那么每个兵营在“已经是问号”的条件下基础概率约为15%÷3=5%；若从任意普通格开始算，还要再乘前一层的25%。

### 2.4 三层随机不要混成一句“翻格随机”

最容易产生误解的说法是“玩家翻一个格，系统随机一张卡”。当前证据更准确的模型是：

```text
普通格初始化
  ├─ 第一层：随机价格档位
  ├─ 第二层：随机内部稀有度
  └─ 第三层：随机具体合法候选
          ↓
      保存隐藏结果
          ↓
玩家之后扩张到这里
          ↓
点击时结算 / 揭晓 / 少量覆盖
```

## 3. 不是所有格子都走这套普通三层随机

### 3.1 模板固定内容优先保留

主城、已打开格、不可开启格、已有`ArchitectureId`/`CardId`以及其他显式内容会优先保留。训练和教程也可以直接预置内容，因此这类格子会绕过普通随机的部分或全部步骤。

### 3.2 主城邻格是结构性配额，不是六个普通随机格

系统分别取得双方主城最多6个邻格，并各自执行一次`ShuffleSix`。洗牌决定用途落在哪里，而不是决定有没有这些用途。

|槽位|用途|结果|
|---:|---|---|
|0|GoldMine|强制金矿，按金矿价格|
|1|OneStar|强制一星，50|
|2|UnCharted|强制问号，25|
|3|Defense|强制防御候选，通常250|
|4|Soldier|只有`SoldierPileHiddenHexEnabled`开启时成立|
|5|None|继续走普通随机|

地图边缘、固定内容或缺失邻位会使这套配额不能完整落地；双方独立洗牌也不保证镜像位置相同。

### 3.3 特殊资源会提前占用位置

竞技场至少为4时，初始化存在一次`Range(0,101)`并以结果小于30作为特殊资源事件入口，离散口径为30/101≈29.70%。命中后会从合法候选中选1或2个位置；每选一个位置，就从候选池移除它以及所有相邻格，因此两个特殊资源点不会紧挨着。成功构建特殊格后，该格不再进入普通档位和兵种随机。

`TryBuildSpecialResourceCell`在不同竞技场进入不同内容分支，但具体资源类型字符串所在共享跳板尚未完全恢复，因此这里只确认触发、数量和不相邻保护。

### 3.4 金矿来自多个来源，不能用一个“固定矿数”概括

一张图的初始金矿至少可能来自：模板预置、主城邻格强制金矿、普通R候选中的随机金矿。`CreateGoldMineLimitState`还能读取总额度和镜像侧额度，对“普通候选里的随机金矿”进行限制。

主城邻格的强制金矿可以绕过普通候选封锁，所以该额度不能直接理解成整张地图最终矿数硬上限。旧`GlobalArenaInfoSheet2.minesCountLimit`到当前`BattleConfigPackage`的完整注入关系尚未恢复，也不应把静态表值直接写成线上实测上限。

## 4. 点击时哪些结果仍可能变化

### 4.1 正常路径：沿用初始化隐藏结果

普通情况下，玩家点开格子后不会重新抽25/50/100/250，也不会从零重跑完整的“稀有度→具体卡牌”链。开格函数优先消费已经生成并保存的格子内容。

### 4.2 低价格子存在高品质重抽/降级路径

`TryApplyFirstThreeCheapOpenReroll`这条路径要求目标价格小于250、存在有效候选、已开低价格计数满足`CountCheapOpenedHexesByPlayer<=3`、候选稀有度至少为RareLevel 3，并排除部分资源和防御结果。命中后会尝试从R候选中重新选择，并排除金矿。

因此一个格子初始化时即使已经是SSR/SSSR，最终玩家点开时也可能被这一点击阶段规则改写。25、50、100属于低价范围，250不属于。函数名带“FirstThree”，但完整计数追加时序仍应以当前代码边界为准，因此这里不把它简化成玩家肉眼可直接数出的“严格前三次必降级”。

### 4.3 祝福、神器和引导也可能后置覆盖

- 神器首次传说升级：满足对应开关、候选来自本局牌组、阵营有效且机会未消耗等条件时，可在已有候选基础上尝试替换为传说候选。
- 超级召唤：`SpendGold`成功扣款后累计祝福进度；本地阈值为2000。达到阈值后进入Ready，之后在合法翻格结果处理中消费并尝试选择传说卡。
- 教程/引导：教程可以预置结果；guidedGame的敌方SSSR还存在按当前档位降级的路径，另有龙骑士强制引导。
- 被占领隐藏格：存在重新生成路径，但会排除已开/不可开格、主城、桥、资源箱、特殊士兵格和部分特殊金卡建筑。

所以“初始化已决定”指的是**基础隐藏结果已经生成**，不是“之后任何逻辑都绝对不能碰它”。

## 5. SSSR加权：这是第二层随机的修正，不是另一套地块生成规则

从系统结构看，这部分只是“内部稀有度抽取”的修正层。它不会把25元格改成250元格，也不会决定某格什么时候显现，因此放在普通生成主线之后理解更合适。

### 5.1 用户标签只增加SSSR权重

当前已恢复的用户标签增量为：

|有效标签|加入本方SSSR段的权重|
|---|---:|
|本方JustPaidUser，刚付费|10|
|本方LosingStreak，连败|50|
|本方InactiveUser，回流|30|
|对手WinningStreak，连胜|50|

这些数字是权重增量，不是直接增加百分点。若当前这组增量合计为B：

```text
P(SSSR) = (基础SSSR权重 + B) / (100 + B)
P(其他结果) = 原权重 / (100 + B)
```

例如一星格基础SSSR权重为1；若只存在连败+50，则这一格在加成尚未消费时的SSSR概率为51/150=34%，而不是1%+50%=51%。

### 5.2 这组用户标签是一次性消费资格

`UserLabelGoldCardOddState`按玩家维护共用消费状态。`ResolveUserLabelGoldCardOdd`在消费位已经成立后，不再返回JustPaid/LosingStreak/Inactive/对手WinningStreak这一组加成。当生成结果满足：用户标签加成仍大于0、最终稀有度为SSSR、且HexType属于兵营类时，该玩家消费位会被置为已消费；之后生成格回到不含这组用户标签的权重。

换句话说，它更像“提高本局稳定生成序列里第一个符合条件的SSSR兵营更早出现的机会”，而不是让整张地图每个格永久维持高SSSR率。消费的是本局生成器的加权资格，不等于清除账号上的连败、付费或回流标签。

没有在当前已恢复链路中发现“出一个SSSR后固定冷却N格”“连续N格不出就逐步加概率”“两个普通SSSR必须隔开”等规则。用户标签消费后，基础SSSR概率仍然存在，之后仍可能再生成SSSR。

账号标签如何触发、清除、扣次和进入匹配载荷，由[匹配与机器人专题](../matching/index.html)维护；本页只解释这些状态进入地块生成后如何影响内部稀有度。

每日祝福和周卡加成是在`ResolveInitialRarity`里的独立来源，不属于`UserLabelGoldCardOddState`这一消费位，也不能和上述用户标签机制混成同一个“保底”。

## 6. seed、Q/R和“内部生成顺序”

`BuildStableGenerationOrder`把seed、Q坐标、R坐标和固定常数混合成64位排序键，再按键逐格生成。它不直接等于模板数组顺序，也不等于从主城向外的空间顺序，更不等于玩家点击顺序。

因此：

```text
同一setupId + 同一seed + 同一双方牌组 + 同一战斗配置
≈ 可复现同一初始化结果
```

例如内部生成顺序可能是：

```text
E → B → H → A → F → C → G → D
```

而玩家实际扩张顺序可能是：

```text
A → F → C → D → B → H
```

如果某个一次性SSSR加权在内部第3个生成格H已经命中并被消费，玩家却第6次才扩张到H，那么主观体验会变成“第6次才出金”。反过来若玩家很早摸到H，又会感觉“第一下就出金”。所以玩家第几次看到SSSR，不能直接反推出生成器是第几次才随机到SSSR。

稳定生成顺序也不等于每格完全独立哈希决定全部结果。逐格生成仍会根据候选池、金矿额度、特殊用途等继续消费确定性随机数；前面某格的候选变化可能影响后续随机流。当前初始化链没有读取战斗秒数，时间流逝本身不会逐渐改变已经生成的档位。

Q/R本身只是六边形逻辑坐标，不是概率参数；详细概念见[Q/R六边形坐标概念专题](../hex-coordinates/index.html)。

## 7. 可开启状态属于扩张规则，不属于随机品质

已恢复的`BattleHexCellState`字段包括：

|字段|偏移|含义|
|---|---:|---|
|`IsEnemyHex`|0x22|格子属于哪一侧|
|`IsOpened`|0x23|是否已打开|
|`CanOpen`|0x24|是否具备基础开放许可|
|`IsBridge`|0x25|是否桥格|
|`IsPlayerMainTower`|0x26|是否玩家主城|
|`IsEnemyMainTower`|0x27|是否敌方主城|

`CanOpen`不是“此刻已经出现在玩家边界”的同义词。`GetHexOpenBlockReason`还会调用`HasPlayerOpenAnchorNeighbor(int playerId, BattleHexCellState target)`遍历`Neighbors`，结合邻格的阵营、opened状态和主城状态判断目标格旁边是否存在有效开放锚点。

`CommitOpenedHex`提交后会进入`ResolveOpenedHexOutcome`，并可能触发相邻特殊奖励与`MarkDynamicWallsDirtyAround`刷新动态墙；`BattleNavigationSystem.SetHexOpened`则负责切换opened状态并标记后续刷新。这些属于开格后的状态和拓扑更新，不是普通品质重新随机。

## 8. 地图骨架从哪里来

`BattleSetupConfig`提供一局地图的格子Q/R、邻接、双方主城、可开启状态以及模板预置内容。不同入口选择地图骨架的方式不同：

|入口|当前已确认行为|
|---|---|
|线上对局|`ApplyBattleCoreServerMapSelection`和`TryGetBattleCoreAuthoritativeMapSelection`可接受服务器给出的竞技场、地图类型、多边形ID和setupId，因此客户端不一定自己随机选图|
|离线对局|有preferredSetupId时先精确匹配；否则按入口模式、竞技场、地图类型和多边形ID扫描并返回第一条完整匹配|
|训练局|使用training setupId和固定`hexConfigs`|
|赛季PVP|同层候选`Weight`当前均为1000；首场另有`Pvp_PlayFirstMap=1001`固定矩形图|

普通竞技场在经典三形与多边形之间的上游最终分流仍未完整恢复。因此，配置里存在某张图，不等于当前线上一定由客户端随机选中它。

## 9. 机制总表：什么阶段决定什么

|机制|阶段|它真正改变的东西|
|---|---|---|

## 10. 当前证据不能回答什么

- 当前服务器针对具体账号实际下发的seed、地图选择、双方牌组、标签和模式开关。
- 经典三形与多边形在普通竞技场入口的最终上游分流。
- UI从authoritative cell state到具体显隐动画的完整调用顺序；当前初始化与开格主链已支持“基础档位预生成”，但表现层还没有逐函数复原完。
- 旧`minesCountLimit`到当前`BattleConfigPackage`的完整注入关系。
- 分包桥接后的完整OpenHex日志时序，以及超级召唤全部合法目标类型。
- 特殊资源内容字符串和所有候选为空时的端到端边界。
- 当前已恢复链路没有发现实时胜率、战斗秒数、固定N格SSSR冷却或固定N格递增保底，但这不能证明所有服务端实验和未恢复分包都绝对不存在这些机制。

## 13. 证据来源与阅读边界

函数级行为结论来自2026-09-11统一主WASM / metadata / C# method-map，并在涉及function-split时交叉检查wasmcode2；静态表和既有界面材料来自2026-09-03本地资源快照。`dump.cs`只用于类型、方法名和RVA定位，不单独作为行为真相。wasmcode2中的`archive_value`仍视为未解释值，不把它当偏移、地址或函数序号。

本页刻意把“玩法解释”和“证据索引”分开：前半部分回答一个格子如何生成和揭晓，后半部分才保留函数、地图池和未确认边界。这样即使以后继续补逆向证据，主叙事也可以继续围绕实际系统决策链，而不是围绕单个历史问题组织。
